# Test utilities

`ast-predicate/test-utils` contains optional helpers for testing compiled SQL generated by predicate adapters or services.

The helpers are intentionally test-framework neutral. The package does not depend on Jest, Vitest, or another test runner. Pass the `expect` function from your test framework.

```ts
import { createCompiledSqlExpect } from 'ast-predicate/test-utils';

const {
    expectCompiledSql,
    expectSelectFrom,
    expectUpdateTable,
    expectWhereEquals,
    expectWhereIsNull,
    expectNoWhereEquals,
    expectSetColumn,
    expectOrderByColumn,
    expectLimitParameter,
    expectParameterOccurrences,
} = createCompiledSqlExpect(expect);
```

## Basic assertion

Use `expectCompiledSql` when you want to check SQL fragments, regular expressions, or parameters directly.

```ts
expectCompiledSql(
    {
        sql: `
            select *
            from "schema"."Articles"
            where "workspaceId" = $1
              and "deletedAt" is null
            limit $2
        `,
        parameters: ['workspace-1', 25],
    },
    {
        contains: ['from "schema"."Articles"'],
        matches: [/"workspaceId"\s*=\s*\$\d+/i],
        parameters: ['workspace-1'],
        exactParameters: ['workspace-1', 25],
    },
);
```

`contains` checks normalized SQL text.

`matches` checks normalized SQL text with regular expressions.

`parameters` checks that the compiled query contains the provided parameter values.

`exactParameters` checks the full parameter array.

## Select query helpers

Use the higher-level helpers for common PostgreSQL select-query assertions.

```ts
const compiled = {
    sql: `
        select *
        from "schema"."Articles"
        where "workspaceId" = $1
          and "categoryId" = $2
          and "deletedAt" is null
        order by "title" asc
        limit $3
    `,
    parameters: ['workspace-1', 'category-1', 25],
};

expectSelectFrom(compiled, 'schema.Articles');
expectWhereEquals(compiled, 'workspaceId', 'workspace-1');
expectWhereEquals(compiled, 'categoryId', 'category-1');
expectWhereIsNull(compiled, 'deletedAt');
expectOrderByColumn(compiled, 'title', 'asc');
expectLimitParameter(compiled, 25);
expectParameterOccurrences(compiled, 'workspace-1', 1);
```

## Update query helpers

Use update helpers for compiled update queries.

```ts
const compiled = {
    sql: `
        update "schema"."Articles"
        set "description" = $1
        where "id" = $2
    `,
    parameters: ['Updated description', 'article-1'],
};

expectUpdateTable(compiled, 'schema.Articles');
expectSetColumn(compiled, 'description', 'Updated description');
expectWhereEquals(compiled, 'id', 'article-1');
```

## Negative where checks

Use `expectNoWhereEquals` when a query must not contain a specific equality predicate.

```ts
expectNoWhereEquals(compiled, 'deletedAt');
```

When a value is provided, the helper also checks that the matching parameter value is not used for that column predicate.

```ts
expectNoWhereEquals(compiled, 'status', 'ARCHIVED');
```

## Available helpers

The subpath exports these functions directly:

```ts
createCompiledSqlExpect(expect)
normalizeSql(sql)
quotedPgTable(table)
quotedPgColumn(column)
```

The object returned from `createCompiledSqlExpect(expect)` contains:

```ts
expectCompiledSql(compiled, assertion)
expectSelectFrom(compiled, table)
expectUpdateTable(compiled, table)
expectWhereEquals(compiled, column, value?)
expectWhereIsNull(compiled, column)
expectNoWhereEquals(compiled, column, value?)
expectSetColumn(compiled, column, value?)
expectOrderByColumn(compiled, column, direction)
expectLimitParameter(compiled, limit)
expectParameterOccurrences(compiled, value, count)
```

## PostgreSQL assumptions

The SQL helpers are PostgreSQL-oriented. They assume double-quoted identifiers such as `"workspaceId"` and positional parameters such as `$1`, `$2`, and `$3`.

This makes them suitable for Kysely/PostgreSQL adapter tests and similar service-level tests, but they are not intended to be database-neutral SQL assertions.

## Recommended use with adapters

Keep adapter tests focused on the SQL generated by the adapter, not on the internal AST builder implementation.

A typical test can build a predicate with `ast-predicate`, pass it to an adapter or service, compile the SQL, and assert the important SQL fragments.

```ts
const predicate = ({ eb, and }) =>
    and([
        eb('workspaceId', '=', 'workspace-1'),
        eb('deletedAt', 'is', null),
    ]);

const compiled = service.buildQuery(predicate).compile();

expectSelectFrom(compiled, 'schema.Articles');
expectWhereEquals(compiled, 'workspaceId', 'workspace-1');
expectWhereIsNull(compiled, 'deletedAt');
```
